# 架构决策

## 2026-09-19：首页收敛为规格单价表

- 原首页重复展示每个规格的大蟹图、礼盒宣传和图文指南，移动端需要多次滚动才能看完。改为一张公母规格单价表，每类只展示一次缩略图，单价读取当前在售配置；每行可进入该规格选购，保留自由搭配和套餐入口。
- 图片展示尺寸由容器决定：移动端 56 × 56px、桌面 80 × 80px，等比例完整显示，不按原图尺寸撑高布局。产地和吃法改为默认折叠、按需展开，购买须知继续默认完整显示。
- 当前 4 种规格下，浏览器模拟 375 × 812、390 × 844、975 × 745、1280 × 800 均一屏显示；320 × 740 下页面高 795px，所有尺寸无横向溢出。规格更多时自然纵向延长，不裁切商品列表。

## 2026-09-19：拼团复用普通下单的多规格搭配

- 旧实现把一个成员限制为一种规格，不符合一个人同时买公母蟹的需求。成员改为一个姓名配多项 `items: [{specId, qty}]`，总数至少 1 只，仍是一条成员记录。
- 普通下单不足 10 只时可携带当前搭配发起拼团；多地址时明确选择其中一个地址的配置，成团后统一寄到团长地址。独自购买仍允许确认后提交。
- 建团和发起人的采购记录原子保存；链接只携带 token，采购配置存在数据库，价格由服务端计算。编辑自己的记录仍使用成员编辑凭据。
- 为兼容历史数据，沿用成员快照保存多项规格，旧单规格记录和请求继续可读写；最终订单合并所有成员的规格数量。成团条件仍为全团总数达到 10 的倍数，且必须团长最终提交。

## 2026-09-19：单一入口，管理员走特殊下单码

- 用户和管理员共用同一个前端入口，去掉页面顶部“预览模式 / 管理端 / 用户端”切换条，避免把演示开关带进正式流程。
- 普通下单码进入用户端；`admin_users` 中角色为 `admin` 或 `superadmin` 的下单码登录后自动进入管理端。`?view=admin` 只作为兼容的登录页入口，不再承担权限门禁。
- 购买须知默认展示活鲜运输损耗说明：会认真打包，但运输途中仍可能有极少量损耗；按 10 只计算最多只能承受 1 只死蟹损耗，出现 2 只就会亏本，实际货损率很低，不能接受这类小概率风险请先不要下单。
- 移动端是用户和管理员的主要工作场景，采用同一套 React 页面配合移动优先断点自适应：用户端单列下单与安全区底栏，管理端保留三项文字导航并优化发货卡片触控，不维护独立的移动页面分支。

## 2026-09-19：新版用户端作为默认入口

- 根路径默认渲染统一登录入口；登录接口返回 `role` 后由 `src/main.jsx` 自动选择 `Storefront` 或 `AdminApp`。管理端不再依赖独立页面开关。
- 旧版 `UserView` 归档到 `docs/archive/legacy-user-view.jsx`，不再挂载。

## 2026-09-19：购物车和订单先走数据访问边界

- 页面层只负责交互和展示。
- `src/storefront/purchase.js` 负责规格、金额、份数和截单规则。
- `src/storefront/addressParser.js` 负责粘贴文本解析。
- `src/storefront/cartRepository.js` 负责本地草稿和预览订单读写。当前用 `localStorage` 做原型存储，后端接入时替换为 API 适配器，页面不直接改数据库。
- 订单完成后保留配置快照，支持“同配置再下单”和继续添加地址；正式提交仍需服务端以中国时区再次校验截单和价格。

## 2026-09-19：以单输入下单码替代账号密码界面

- 按用户要求，入口只保留下单码输入框与「登录」按钮，输入有效下单码即可保存在当前浏览器。
- 下单码由服务端校验并作为轻量 bearer 身份凭据：普通用户只能读取自己的订单；管理员下单码返回服务端角色并自动进入后台，浏览器自报 `role` 不生效。
- 下单码保存在当前浏览器只是开发阶段的会话实现，后续商用版本迁移到短期 HttpOnly 会话；不能仅凭可猜测的姓名加后缀返回姓名、电话和地址。

## 2026-09-19：下单码允许新用户直接进入

- 下单码长度为 1～64 个字符，只允许中文、英文字母和数字，不允许空格或其他特殊符号。
- 英文字母登录时不区分大小写，服务端和浏览器统一按小写保存/比较；中文保持原样。
- 首次输入格式合法且尚未存在的下单码时，服务端自动创建普通用户，显示名取连续的中文前缀；不再要求管理员提前手工建用户。
- 管理员下单码仍优先匹配 `admin_users`，通过同一个入口自动进入后台。

## 2026-09-19：超级管理员初始化方式

- 管理员以 `superadmin` 角色存储在 `admin_users`，可通过统一下单码登录进入后台；管理员请求使用 `X-Order-Code`，服务端按数据库角色授权。
- 不把固定超级管理员写入通用 seed。开发或生产环境需要显式执行 `npm run provision:superadmin -- <下单码>`；已存在账号幂等，普通用户或冲突管理员不会被覆盖。
- 旧 `Authorization: Bearer` 管理员令牌暂时兼容，便于部署过渡；新前端统一使用下单码。

## 2026-09-19：履约流程保持轻量

- 用户下单后，管理员按订单顺序安排捕捞、按配置打包、按顺序称重和发货。
- 每个地址订单打包后由管理员登记实际运费，提交即发货；后续可修改金额，不可清空，免运费明确填 0。系统据此重新计算用户最终应付金额。
- 用户登录后只需要看到蟹款、包装费、运费和合计金额构成。
- 当天截单批次默认当天发走，不引入用户确认、付款状态、待结算、已付款、已完成或多级核销状态机。
- 允许管理员删除订单；实现时保留最基本的操作记录，避免为了“核销”引入复杂流程。

## 2026-09-19：套餐按地址和 10 只一盒配置

- 套餐由管理员在后台配置，前台只读取当前启用的套餐模板，不把公母组合写死在页面代码里。
- 计算单位是一个收货地址的单份订单；每份按 10 只为一盒计算，同地址多份按份数累加。
- 一个套餐可以配置 5 公 5 母等任意公母数量、不同规格混合，也可以配置为全公或全母；每盒总数必须为 10 只。
- 套餐、规格、价格和包装规则需要在下单时保存快照，后续修改后台配置不能改写历史订单。

## 2026-09-19：管理端采用卡片和顺序手势

- 管理端首屏先展示当前批次总数和公母规格捕捞汇总，再进入按顺序排列的地址发货卡片。
- 履约状态只保留三层：捕捞中、已打包、已发货。配送是现场动作，不单独建立“配送中”状态。
- 上下滑动只负责切换订单；捕捞中左滑标记为已打包；已打包右滑可撤回捕捞中。
- 已打包左滑打开该地址的快递费录入；管理员提交快递费后，服务端在同一事务内把订单直接标记为已发货并更新最终金额。
- 已发货订单允许修改快递费，但不允许清空快递费或回退状态。
- 升级迁移 `004_three_shipment_statuses.sql` 将旧配送记录按运费是否已登记映射为已发货或已打包；历史迁移保持不动。迁移已通过内存数据库升级测试，远程环境未执行。
- 手势必须有状态提示、撤销反馈和误触保护，现场测试优先于增加更多按钮。

## 2026-09-19：正式版本采用前后端分离和真实数据库

- 当前 React/Vite 页面仅作为 UI 基线；正式版本必须拆分为独立前端、后端 API 和数据库服务。
- 前端不得直接连接数据库，也不得把订单、价格、运费、用户身份或履约状态保存在浏览器作为生产数据源。
- 后端负责鉴权、参数校验、金额计算、截单、库存、订单状态、幂等和审计；数据库负责事务、约束、索引、迁移和持久化。
- 正式上线必须具备开发、测试、生产环境隔离，HTTPS、日志、备份恢复、权限分级和回滚流程。

## 2026-09-19：拼团链接公开查看采购情况

- 拥有拼团链接的人都可以查看该团成员姓名、规格、数量、总只数、成团进度和金额汇总。
- 成员不填写地址，只提交姓名、规格和数量，数量最少为 1 只。
- 总数量达到 10、20、30…只时，拼团具备成团条件；只有团长补充/确认收货地址并最终提交后，才进入发货队列。
- 结单前后都保留金额查看；发货称重后再展示每个成员按实际蟹重分摊的运费。

## 2026-09-19：价格全部后台配置

- 蟹价、包装价、套餐价和运费参数均由管理员后台配置，开发环境可以使用任意测试价格。
- 价格具体数值不作为开发阻塞项；订单仍需保存下单时的配置快照。

## 2026-09-19：购物车和提交按钮分工

- 选购页在“厚礼蟹”旁提供“加入购物车”。
- “加入购物车”只保存当前规格、包装和地址为订单草稿；不锁库存、不生成订单号、不进入履约。
- “厚礼蟹”只提交当前订单；购物车可以编辑、删除和继续提交草稿。
- 拼团成员提交的是拼团意向，不走个人购物车结算；团长页负责汇总和最终提交。

## 2026-09-19：阶段 0 规则评审会结论

> 其中实重录入与分摊口径已由下方“只填快递费”决策取代，保留此节作为历史记录。

1. 每盒容量固定 10 只，系统常量 `BOX_CAPACITY=10`，不做后台配置项。
2. 自定义数量盒数 = `max(1, ceil(总数/10))`，包装费按盒数计；0 只不允许提交。
3. 订单编号：每批次从 0001 重排，数据库 `(batch_id, seq)` 联合唯一整数序列，服务端事务内生成；对外展示格式 `D{YYMMDD}-{NNNN}`（示例 `D260919-0001`）；超 9999 自然变 5 位，不断序列。
4. 运费：按发货单元录入实际运费。个人订单一个发货单 = 一个地址 = 一个包裹，管理员在已打包阶段逐地址直录实际运费，提交后直接发货；已发货订单允许修改，不允许清空。拼团录入拼团总运费，按成员实际蟹重比例分摊：`q_i = floor(F × w_i ÷ W)`，余数 `R = F − Σq_i` 按成员提交顺序前 R 名各补 1 分，总和恒等；允许单成员人工改价（必填原因、写审计、差额归集到团长）。废止“批次总运费按重量分摊”的旧表述。
5. 实际蟹重与快递费同一表单一次提交（已打包卡片左滑进入）；提交快递费后直接变为已发货。输入单位“两”（允许一位小数），存储整数克（1 两 = 50 克）。
6. 下单码：1～64 个字符，仅允许中文、英文字母和数字，英文不区分大小写；首次合法输入自动建立普通用户，管理员码优先进入后台；长期有效、可停用/重置，即身份凭据（bearer 性质），凭码只能读自己的订单；换设备重输同码。
7. 删除订单：软删除 `orders.deleted_at` + `audit_logs` 记录操作者、订单编号、删除时金额快照、原因、时间。
8. 技术栈：Fastify + better-sqlite3 + 编号 SQL 迁移文件（`server/` 独立 npm 包）。理由：单人小生意、零外部依赖当天可跑可测；事务/外键/唯一约束/迁移/幂等门槛全满足；SQL 收敛在 DAO 层用标准语法，PostgreSQL 保留为未来迁移目标。
9. 购物车草稿：服务端 `cart_drafts` 关联下单码用户，凭码跨设备恢复；不锁库存、不生单号、不进履约；提交后删除对应草稿。
10. 拼团建模：团长最终提交 = 一笔订单 + 一个发货单（与个人订单同构，同一套状态机）；成员作为该订单下行项（姓名/规格快照/数量/实际蟹重克/分摊运费分/人工修正标记）承载分摊。

## 2026-09-19：首次生产部署形态与本地开发交接

- 部署形态：Ubuntu 上 nginx 监听 `7648` 托管前端 `dist/` 并把 `/api` 反代到后端 `127.0.0.1:7649`；后端由 systemd `crabshop.service` 托管（`User=crabshop`、`NODE_ENV=production`、`DATABASE_PATH=/opt/crabshop/data/app.db`、`ADMIN_TOKEN` 经 `/opt/crabshop/server/.env` 注入）。80/443 被机器上 docker 占用，故不占用；对外反代、域名和 HTTPS 由用户自行配置，项目和部署脚本不接管。
- 服务器 Node 环境：`/usr/bin/node`（systemd 和脚本统一用它）；root 的 fnm  Node 在 `/usr/local/bin`，`sudo -u crabshop` 没有 npm PATH——服务器上跑维护脚本一律用 `/usr/bin/node scripts/xxx.js` 并带 `DATABASE_PATH`，执行后 `chown -R crabshop:crabshop /opt/crabshop/data`。

## 2026-09-19：地址解析规则（顺序无关）

- 姓名、电话、地址三个字段**任意顺序**都要能解析，不按固定位置硬切。实现顺序：先归一化（全角数字字母折半角、全角空格与各类破折号统一）→ 剥离数量段 → 用 `/(?<!\d)1[3-9](?:[ \t-]?\d){9}(?!\d)/` 定位手机号并挖掉 → 剩余片段按地址特征词与「2-4 个纯中文」区分地址和姓名。
- 手机号必须严格 11 位：12 位不能被贪婪匹配吞成 11 位后把多出的数字甩进地址（旧实现的真实缺陷），要按「疑似号码簇」整段识别并报错。
- 回归测试：`node scripts/address-parser-selftest.mjs`，36 项用例，当前 36/36。新增解析场景先补用例再改实现。

## 2026-09-19：下单码空白与全角处理

- 下单码允许中文、英文字母、数字任意组合。中文输入法下输入时常带入空格（半角 U+0020 / 全角 U+3000），旧实现直接报「不能包含空格」，用户不知所以。
- 改为：`normalizeOrderCode` 先剔除所有空白（含全角空格、制表符、Unicode 空白），再把全角数字字母折半角，最后转小写；`validateOrderCode` 校验规范化后的结果。前后端两份实现逐字一致。
- 下单码要经 `X-Order-Code` 头传输，HTTP 头只能是 latin-1，因此中文下单码**必须** `encodeURIComponent` 编码、服务端 `decodeURIComponent` 解码。自写脚本/工具调用接口时同样要编码。

## 2026-09-19：控件高度统一（PC / 移动各一套）+ 团购页布局跳变修复

### 控件高度：病根是「高度靠内边距撑」
- 实测：PC 首页一个页面就有 **70/58/55/44/42/40/36 七种**按钮高度；移动端五种。
- 对策：**高度由 `height` 钉死、上下内边距归零**。PC 一套、移动一套，各自内部必须完全一致：
  - PC（≥641px）：控件一律 **32px**（主次靠颜色区分，不再区分高度）
  - 移动（≤640px）：控件一律 **44px**；输入框字号统一 **16px**（低于 16px 时 iOS Safari 聚焦会把整页放大）
- 豁免：版式大块（品牌区、顶部导航）与多行控件（`textarea`、两行选项、开关）不参与统一。
- 实测：PC 1024/1440 均为 `32px × 14`；移动 390 为 `44px × 12` —— **从 7 种收敛为 1 种**。

### 团购页「布局跳脱、突然放大」
- 根因一：`group.css` 用 `@media (max-width: 520px)` 在 1 列/2 列之间**一刀切**，同时把步进按钮 32→40、数字框 40→44、字号 15→16px，于是 521px 两侧突变。
- 根因二：两列时每列仅 ~235px，「规格名 + 单价 + 步进器」抱不下触发换行 → 行高在 **75↔93px** 之间反复跳。
- 修法：栅格改 `repeat(auto-fit, minmax(280px, 1fr))`，去掉列数断点，尺寸交给统一层。**下限 280px 是实测结论**：列宽 274px 仍换行、286px 才稳定。
- 实测（19 个宽度 320→1440）：**行高恒定 75px**，列数只在 600→640 之间切换一次，零横溢。

### 费用均摊：合并 + 抹零（子 Agent 交付，父 Agent 复跑验证）
- `allocateFreight` 去掉「余数按顺序补给前几名」，改为**抹零**：`Σshares <= totalCents`，且每份都不超过精确值 —— 谁都不会多付。
- 新增 `allocatePackagingAndFreight`：**运费 + 包装费合并成一份总额一次性分完**，仍返回两项明细，且两项之和恰等于该成员份额。结单前没有运费时只分摊包装费，不凭空造运费。
- 后端测试 **105 → 115 项全绿**（父 Agent 亲自复跑确认，非子 Agent 自报）。

### 一、规格排序口径定版：高品质（贵）置顶

## 术语重构与发货复制（2026-09-20）

### 一、术语定版：只留「预设套装 / 自定义套装」，容器叫「我的套装」

乱象：同一个东西后台叫「套餐」、前台叫「套餐模板」、代码里叫「模板」；用户自己配的叫「自由搭配」；容器叫「购物车」，
里面装的东西却叫「草稿」——**用户要记五六个词才能描述一件事**。

定版（用户拍板）：

| 概念 | 说法 |
| --- | --- |
| 用户自己搭配的整套 | 自定义套装 |
| 管理员配好的固定搭配 | 预设套装 |
| 装套装的页面 | 我的套装（原购物车） |
| 列表条目 | 套装 N（原"草稿 #N"） |

- **两个类型装进一个容器**，都能"直接下单"、也都能攒着一起下单（一条套装 = 一个地址）。
  这样只有一个入口，用户不用学两套流程。
- **拼团不引入套装概念**——成员一律自由选配。
- 代码层类名/接口名（`cart_drafts` / `cartRepository` / `.jd-cart-button`）**保持不动**：改它们没有用户价值、只有回归风险。

### 二、预设套装"点一下直接进填地址页"

用户口径是 A：**预设套装 = 搭配已经定好，点一下直接批量发起，不应再让他过一遍选蟹页**。

### 五、刷新后产生重复草稿（2026-09-20 修复）

`saveToCart` 只在 `activeDraftId` 非空时更新草稿，否则新建；而 `activeDraftId` **不持久化** ——
**刷新页面后再「加入套装」就会多出一条内容完全相同的草稿**（实测测试库出现草稿 #1 / #2 一模一样）。

定版口径：**「我的套装」只有一份清单**。没有 `activeDraftId` 时先 `listDrafts()` 复用已有草稿，
有就更新、没有才新建。

实测：加入 → 刷新 → 加入 → 刷新 → 加入，`cart_drafts` 恒为 1 条，且 `updated_at` 持续更新（证明是 update 不是 insert）。
