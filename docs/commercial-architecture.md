# 正式商用架构和工程标准

## 目标

本项目按可上线、可维护、可追溯的商用系统建设。现有 React/Vite 页面是 UI 参考，不能直接把浏览器本地数据当作生产订单。

## 系统边界

```text
用户端 / 管理端前端
          │ HTTPS + 版本化 API
          ▼
       后端服务
          │ 事务、鉴权、业务规则
          ▼
       PostgreSQL
          │
       备份与监控
```

- 前端只负责展示、表单、手势和交互反馈。
- 后端负责身份、权限、价格、套餐、截单、订单、拼团、发货单、运费和状态变更。
- 数据库负责持久化、事务、约束、索引和历史快照。
- 管理端和用户端可以共用后端 API，但必须按角色控制数据范围。

## 推荐技术基线

- 前端：现有 React + Vite，逐步拆出用户端和管理端路由；API 请求集中在数据访问层。
- 后端：Node.js + TypeScript，采用 NestJS 或 Fastify 组织模块、鉴权、校验和 API 版本。
- 数据库：PostgreSQL；使用 Prisma、Drizzle 或等价迁移工具，禁止手工改生产表结构。
- API：REST/JSON，使用 OpenAPI 描述契约；错误码、分页、时间和金额格式统一。
- 部署：前端静态资源和后端服务独立部署，数据库独立托管；开发、测试、生产配置分离。

具体框架可以调整，但不得改变前后端分离、真实数据库、服务端校验和可回滚的底线。

现阶段实际落地为 Fastify + better-sqlite3 + 编号 SQL 迁移文件（`server/` 独立 npm 包），SQL 收敛在 DAO 层使用标准语法；PostgreSQL + Prisma/Drizzle 降级为未来规模化后的迁移目标。前后端分离、真实数据库、服务端校验和可回滚的底线不变（见 `docs/decisions.md` 2026-09-19 评审会结论第 8 条）。

## 最小数据域

- `users`：用户、登录凭据和状态。
- `admin_users` / `roles`：管理员和权限。
- `batches`：发售批次、截单时间和批次状态。
- `specs`：公母、重量规格、售价和启停状态。
- `packages` / `package_items`：按地址每份 10 只的套餐模板及规格组合。
- `orders` / `order_addresses`：订单、用户归属、地址和配置快照。
- `shipments`：每个地址的捕捞、打包、已发货状态和快递费（实际重量字段仅兼容旧接口）。
- `freight_records`：运费、修改人、修改时间和当前有效值。
- `freight_allocations`：发货单总运费、成员规格标重合计、分摊比例、分摊金额、舍入余数和人工修正记录。
- `groups` / `group_members`：拼团和成员；成员至少保存姓名、规格快照、数量和分摊运费，不保存独立收货地址，团长最终订单保存拼团地址。
- `points_accounts` / `points_ledger`：积分账户和不可变积分流水，关联来源订单、兑换记录、幂等键和操作者。
- `audit_logs`：关键状态、金额、运费和删除操作记录。

金额统一使用整数分或数据库 decimal，禁止使用浮点数；时间统一存 UTC，展示按 `Asia/Shanghai` 转换。

## 必须具备的后端能力

- 所有订单创建、运费修改、状态推进和删除动作都需要鉴权、参数校验和服务端权限判断。
- 订单创建必须幂等；同一请求重复提交只能得到同一订单结果。
- 价格、套餐、包装和截单规则在订单创建时保存快照，后续配置变更不影响历史订单。
- 状态推进必须校验当前状态；左滑、右滑只是前端触发方式，不能绕过服务端三态状态机。已打包提交快递费时，状态和金额必须在同一事务内变为已发货。
- 运费修改必须在事务中更新当前值并写入操作记录，用户查询立即得到最新金额。
- 个人运费逐地址直录；拼团按服务端订单快照中规格标重 × 数量分摊该发货单总运费，保证成员运费之和与该单总运费一致；推算重量不写为实重；人工修正必须保留原因和操作者。
- 拼团只有在总数量达到 10 的倍数且团长最终提交后，才允许生成可履约订单；成员页面的动态汇总不能直接触发发货。
- 删除订单应采用受权限保护的软删除或删除标记，保留必要审计信息。
- 管理端汇总必须从数据库订单聚合，禁止继续使用静态数字。
- 拼团分享链接授予该团的只读查看权限，允许查看成员姓名、规格、数量、总数、成团进度和金额；只有团长凭有效操作权限可以补地址和最终提交。

## 安全和可靠性

- 密码、令牌和数据库凭据不得进入前端包、日志或 Git。
- 用户只能读取自己的订单和地址；管理员按角色读取和操作后台数据。
- 手机号、地址等个人信息按最小权限展示，日志中脱敏。
- API 需要限流、输入长度限制、统一错误处理和超时策略。
- 数据库要有每日备份、恢复演练、迁移记录和回滚方案。
- 生产环境必须启用 HTTPS、结构化日志、错误监控和健康检查。

## 商用验收门槛

- 前端、后端和数据库可以独立构建、部署和回滚。
- 个人下单、多地址、拼团、后台顺序处理、运费修改和用户金额查看均走真实 API。
- 浏览器清空缓存、换设备或重复点击不会丢失订单或产生重复订单。
- 截单、价格、套餐总数、权限和状态变更均由服务端最终判定。
- 自动化测试、接口契约测试、数据库迁移测试和关键浏览器流程测试通过。
- 完成备份恢复、权限越权、重复提交和并发更新演练后，才允许上线。
